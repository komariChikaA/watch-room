# Watch Room

一个面向小型社群、朋友或社团使用的私人放映室 / 屏幕直播项目构想。

目标是实现：

- 主持人共享整个电脑屏幕、指定窗口或应用画面
- 支持播放本地视频、网页视频、PPT、游戏等内容
- 观众通过浏览器直接进入房间观看
- 支持系统声音与麦克风
- 尽量降低延迟，并兼顾中国大陆网络环境
- 不依赖商业会议平台的会议时长限制
- 后续可加入文字聊天、语音频道、房间权限和观众管理

## 如何运行

需要 Node.js 20 或更新版本。

```bash
npm install --prefix server
npm install --prefix web
npm test
npm run dev
```

然后打开 <http://localhost:5173>。

主持人在自己的电脑上创建放映室并开始放映。系统会弹出屏幕共享窗口，记得勾选分享音频，观众才能听到声音。

把房间链接发给观众。同一台电脑直接打开即可。同一局域网里的其他设备，把链接中的 `localhost` 换成主持人电脑的局域网 IP。主持人页面要留在 localhost 或 HTTPS 上，浏览器才允许截取屏幕。

房间数据在服务器进程的内存里，重启后会清空。一个人离开后，房间还会保留大约 10 分钟。

生产环境：

```bash
docker compose up --build
```

然后打开 <http://localhost:8787>。

内网试用（其他人用电脑上的局域网地址打开，屏幕共享和麦克风需要 HTTPS）：

```bash
npm run lan
```

第一次打开时，浏览器会提示证书不受信任，选择继续访问即可。

## 当前实现

这一版是小房间里的浏览器放映：

- 创建房间、房间密码、邀请链接
- 主持人分享屏幕，观众用浏览器看
- 在线人数、文字聊天
- 主持人可以停止放映，也可以把观众移出房间
- 主持人刷新页面后，可以用保存在这台浏览器里的身份回到房间
- 同步播放：主持人可以上传一部影片，也可以填一个大家都能打开的视频地址，或播放内置示例。播放、暂停和拖动进度会跟着主持人走
- 文字聊天会同时从画面上飘过，可以关掉弹幕
- 语音频道：加入后能听到房间里其他开着麦克风的人。语音和影片声音是分开的。屏幕共享会去掉本页播出的语音；如果浏览器拆不开，把「语音播放到」改成耳机或虚拟声卡，影片声音可以继续共享

屏幕分享时，主持人的浏览器要给每位观众各发一路画面，所以适合朋友间的小房间，建议不超过 8 位观众。人再多，或者要长时间稳定地播高清视频时，应该改成 OBS 推到 SRS。那部分还没做。同步播放不传画面，只对齐进度。上传的影片由这台服务器发给每个人；如果填的是外部地址，每个人都要能打开那个地址。语音也是每人互相连线，人一多就会吃紧。

也还没做：多清晰度，以及 OBS 推流。

## 实现思路

### 方案一：OBS + SRS

更适合“一个人播放，很多人观看”的放映室模式。

```text
主持人电脑
  │
  │ OBS 捕获桌面 / 窗口 / 视频 / 系统声音
  ▼
SRS 流媒体服务器
  │
  ├─ WebRTC / WHEP
  ├─ HLS
  └─ HTTP-FLV
  ▼
浏览器观众
```

主持人使用 OBS 捕获桌面、指定窗口、播放器或游戏画面，并将视频和系统声音推送到自建的 SRS 服务器。

观众只需要打开网页即可观看，不需要安装客户端。

优点：

- 对桌面投屏和视频播放都比较通用
- OBS 可以精确控制分辨率、帧率和码率
- 比传统 Zoom 类会议更适合连续播放高清视频
- 服务端可以完全自建
- 可以根据人数扩展服务器和带宽

建议第一版采用：

- 1080p
- 30 FPS
- H.264
- 4–6 Mbps
- WebRTC 低延迟播放

### 方案二：MiroTalk BRO

如果希望快速做出类似“会议链接”的体验，可以直接基于 MiroTalk BRO 自建。

```text
主持人浏览器
  │
  │ Screen Share
  ▼
MiroTalk BRO / SFU
  ▼
多个浏览器观众
```

适合：

- 临时屏幕共享
- 小规模共同观看
- 希望观众点击链接即可加入
- 同时需要聊天、麦克风等功能

相比 OBS + SRS，部署和使用更接近 Zoom，但在大量观众和长时间高清视频播放方面，流媒体架构更合适。

### 方案三：同步播放器

如果所有人都能访问同一视频源，可以不真正直播视频，只同步播放状态。

```text
             WebSocket 房间服务器
                │
       play / pause / seek
                │
      ┌─────────┼─────────┐
      ▼         ▼         ▼
    用户 A     用户 B     用户 C
      │         │         │
      └──── 同一视频源 ────┘
```

服务器只同步：

- 播放
- 暂停
- 跳转
- 当前时间
- 房间状态

视频本身由每个客户端直接读取本地文件、对象存储或 CDN。

这种方式服务器压力最低，也最容易支持大量用户。

## 推荐架构

项目后续可以采用混合方式：

```text
                     ┌─────────────────┐
                     │  Watch Room Web │
                     └────────┬────────┘
                              │
              ┌───────────────┼───────────────┐
              │               │               │
              ▼               ▼               ▼
          Room API        WebSocket         Chat
              │         播放状态同步          │
              │                               │
              ▼                               ▼
        SRS / WebRTC                    Socket.IO
              │
              ▼
          视频与屏幕
```

建议技术栈：

- Frontend: React / Vue
- Backend: Node.js / Go
- Room Sync: WebSocket / Socket.IO
- Streaming: SRS
- Broadcaster: OBS
- Voice: LiveKit / mediasoup（可选）
- TURN: coturn
- Reverse Proxy: Nginx
- Deployment: Docker Compose

## 中国大陆网络考虑

如果主要用户位于中国大陆，应优先选择大陆或大陆网络质量较好的服务器。

WebRTC 部署建议同时提供：

- UDP
- TCP fallback
- TURN
- TURN over TLS

可使用 coturn 处理复杂 NAT、校园网、公司网络和部分移动网络下的连接问题。

## 第一阶段 MVP

第一版只实现最核心的功能：

1. 创建 / 加入房间
2. OBS 推送桌面或视频
3. 浏览器低延迟观看
4. 房间在线人数
5. 简单文字聊天
6. 房间密码
7. 主持人开始 / 结束放映

之后再逐步增加：

- 多清晰度
- 弹幕
- 语音频道
- 房主 / 管理员权限
- 邀请链接
- 播放历史
- 同步播放器模式
- 本地视频文件同步
- 多房间
- Docker 一键部署

## 核心原则

本项目不追求完整复刻 Zoom。

主要目标是：

> 用更简单的架构实现“一个人投屏 / 播视频，多人稳定观看”的私人放映室。

对于大量观众，优先采用广播和流媒体架构，而不是让所有用户互相建立完整的视频会议连接。
